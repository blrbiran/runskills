## 这个 skill 做什么

帮你**写或改写"讲解型"技术文章/文档**——目标是让**指定读者**(尤其第一次接触该主题的人)能顺畅读懂。它不追求辞藻,只追求:读者读完真的懂了、且不觉得累。

它捕捉的是一套**方法**,不是模板。核心信念:一篇文档合不合格,唯一的裁判是**目标读者读起来的体验**,不是作者觉得"信息都写全了"。作者和读者共享的上下文越多,越容易写出"自己看得懂、别人看不懂"的东西——这个 skill 就是用来对抗这种盲区的。

## 动笔前先定读者(新写、改写都要做)

这是整个流程的第 0 步,写新稿和改旧稿都一样。动笔前先明确四件事,并在心里(或和用户确认)对齐:

1. **写给谁看?** 第一次接触的小白 / 已入门想深入的人 / 同领域专家。**读者定位直接决定语气和详略**,这一步错了后面全错。
2. **不是什么?** 明确边界——不是使用手册?不是论文综述?这能防止跑偏。
3. **读者读完要能做什么/懂什么?** 目标清晰,才知道哪些该展开、哪些可略过。
4. **一句话主旨是什么?** 逼自己回答:"如果读者只记住一句话,那句话是什么?" 说不出这句话,往往是主旨还没想清——先想清再动笔,整篇才有主心骨。

定好这四点,再按下面的工作流动手——**新写**和**改写**的前段略有不同,后段一样。

## 核心写作原则

### 1. 用"讲解体",不是"电报体"

- 写**完整的句子**,有连接词和过渡,让读者能顺着逻辑走;不要用 `A→B→C`、分号串碎片来堆信息。
- **先给直觉或类比,再上术语和精确定义**。读者要先"大概懂了是怎么回事",才接得住严谨表述。(类比怎么挑、什么时候反而会害人,见原则 11。)
- 语气是**引导式**的:像一个懂行的人耐心讲给你听,而不是甩给你一份备忘。但仍然专业、克制,不啰嗦。

### 2. 术语第一次出现,用一句白话解释

不要假设读者已经懂 RAG、embedding、HNSW、cross-encoder 这类词。**首次出现时给一句白话解释**(不必单开术语表)。宁可多一句解释,也不要让读者卡在一个不认识的词上。

### 3. 举例必须无歧义

例子是讲解的利器,但**写不好的例子比不举更糟**——读者会先花力气解析你的例子本身。

- **明确标注这是例子**:用"举个例子""比如"引出。
- **避免会被误读的符号**。反面教训:写 `图这个概念(比尔·盖茨 —创办→ 微软)`,读者第一眼会以为"图是比尔·盖茨提出的"。
- 改成无歧义的写法:"举个例子:「比尔·盖茨」和「微软」是两个实体节点,它们之间连着一条「创办」关系边。"
- **自检法**:把自己当成第一次读的人,问"这句话会不会有第二种理解?"

### 4. 详略"不一概而论"——该扩的扩,该缩的缩

补细节和背景,但**要把控"度",不能补得细碎**。具体地:

- **扩写**:概念性的"为什么"、读者最关心的核心机制、抽象且陌生的部分。
- **精简**:和正文重复的收尾/总结、读者已经懂的铺垫、为凑篇幅的话。
- **保持紧凑**:表格本就该密,不用改成散文;进阶/实现细节做成旁注。
- 一句话:**详略跟着"读者在这里需要多少"走**,不是每段都一样详细。

### 5. 用一个"贯穿全文的例子"落地抽象

选一个具体场景(如"假设你攒了 500 篇资料想让 AI 回答问题"),在每个抽象概念处**回到这个例子**看它怎么工作。比起干讲定义,读者跟着一个熟悉的场景走,理解成本低得多。

### 6. 结构先行,并给"导读"

- 开头先交代:**写给谁看 / 不是什么 / 怎么读**(哪部分先读、各部分讲什么)。读者知道自己在地图的哪里,才不慌。
- **先给全局框架,再展开细节**。让读者先有骨架,再填肉。
- **按"信息 DAG"排序**:知识是一张有向无环图,后面的概念依赖前面的。排章节和段落顺序时,确保读者读到某个概念时,它所依赖的前置概念**都已经讲过**了——绝不能用一个还没解释的词去解释另一个词。这是"术语首次出现要解释"的结构版:不只单点解释,整篇的讲解顺序也要顺着依赖走。
- 长文用清晰的分部分/分节 + 一句话的"这节讲什么"。

### 7. 主线和旁注分离

把"进阶内容、实现细节、某个具体项目的做法"从主线里择出来,做成**视觉上可区分的旁注**(如引用块),并明确告诉读者**"第一次读可以跳过,不影响主线"**。这样主线保持顺畅,想深入的人也有料可挖。

### 8. 诚实,并且把风险标在它出现的地方

- 没亲自核实的数据(benchmark 数字、性能指标)**标注来源**,并提示读者/用户"如需严谨发布请核对原始出处"。不把"大概是"写成"就是"。
- 有取舍、有局限就如实写出来,不夸大某个方案。读者信任来自诚实,不来自绝对化的措辞。
- 技术类长文值得在**文末单开一节「关于本文的准确性」**,把内容分成三桶:**在代码/仓库里核实过的**、**实际跑过的**、**来自既有知识但没核对官方文档的**。三者的可信度差一个量级,读者最该警惕的恰是第三桶。**桶是空的也要把空写出来。** 一篇没跑过任何系统的文章,把"实际跑过的:无"当成一句明确的断言摆在那里,比省略它有用得多:它会拦住下游的人——尤其是接手改写的 agent——把你的结论说成"经过实测验证"。省略会被读成"作者没提,大概跑过吧"。
- **"核实了他们这么说"不等于"核实了这话是对的"。** 归进第一桶的东西里,有一类特别容易蒙混过关:你去源仓库读到了原话、逐字引对了、也标了出处,可**那句原话自己又引了别人当依据,而那个依据不成立**。真实教训:一个项目的设计文档写"长周期评测一致显示,写下了什么比怎么索引更重要",后面挂了一篇论文编号。核对下来编号没错、标题没错,但**论文根本没有这个结论**——它花最大力气证明的恰恰是索引侧的优化有效,方向是反的。如果只核到"这个项目确实这么说"就收手,你的文章就成了这个误读的下一个传播环节,而且因为你引得一字不差,读者更没有理由怀疑。所以:**凡是你的材料自己引了别人**(论文、benchmark、另一个项目),要么顺着再核一层,要么把这句话明确归到"这是某某自己的判断",别让它读起来像有第三方背书。顺着核了一层的话,也要如实写清核到什么深度(读了摘要还是通读全文),否则你只是把一个二手指控当成一手判断在用。
- **同一份材料里两处说法相反时,别只写你信的那一个。** 上一条说的是材料引了别人,这一条说材料**自己跟自己打架**:函数说明和函数体、注释和代码、设计文档和实现,都会各说一套。真实教训:一个函数的说明写着"本地改动会在 pull 时被覆盖",而它下面的代码第一件事就是"本地改过就跳过"。这种冲突里**以能跑的那个为准**通常没错,可**只写你采信的那一个是错的**——读者拿着另一份材料去核,只会以为你写错了,而你连让他判断的机会都没给。所以就地补一句:另一处说了什么、你为什么不采信它。这仍然是原则 13「就地」:冲突提示要长在那句结论旁边,只写在文末等于没写。顺带一个副产品——**两处打架本身往往就是值得写的内容**,它说明那个项目有一处没对齐,而读者照着文档抄就会抄反。
- **"它没有 X"这类负面断言,强度全看你搜了多大范围,而这个范围必须写出来。** 正面断言找到一处证据就成立,负面断言要的是"找遍了都没有",可作者几乎从不交代自己找了多大一圈。真实教训:我断定某个常量"只声明、没接线",grep 了两个目录就觉得证实了,全仓扫一遍才发现它有使用点——**分母是全仓,不是你这轮打算看的那几个目录。** 落到文章里也一样:把"它没有这个机制"写成"本文在某某范围内没有找到,也没有穷尽搜索过",读者才知道该打几折。还有一层:**负面断言比正面断言更容易随版本失效**(新版本可能刚好补上了它),所以这类句子最该挂上版本基准,见原则 9。
- 但**光有文末那一节不够**:半路就去动手的读者永远看不到它。所以哪一段的内容属于第三桶,就在**那一段的开头**再点一句(例:"这一节的配置写法没有对着官方文档逐字核对,配不通先查它自己的文档")。这是原则 13「就地」在诚实这件事上的实例:风险提示要长在风险旁边。

### 9. 引用要指向不会腐烂的坐标

文档的寿命通常远长于它引用的那些坐标。最脆的是**代码行号**:在大家都用 AI agent 批量改代码的当下,你今天写下的 `handler.py:561` 过几天就可能指到别的地方。**一个错的行号比没有行号更糟**,因为它让读者以为你给了精确位置,于是去纠结那一行为什么不对。

所以定位要给**能被搜到的东西**,而不是能被数出来的东西:

- **代码** → 给 `文件路径` + `函数名 / 类名 / 常量名`(例:"`litellm/router.py` 的 `_set_model_list()` 里"),人能 grep,agent 也能。真要给行号,就明确写"截至 X 版本,行号会漂移,请按函数名搜"。
- **"目前最新的是 X" / "只有 A 和 B 支持"** → 别把当下的事实写成永久事实。锚点按优先级选:**最好只给查法**(一条能自己跑出答案的命令——它把一句会腐烂的断言换成一个不会腐烂的能力);**其次钉版本号**(git tag 或 package.json 的版本,而且要真的确认该版本下断言成立,不是拿工作区快照冒充);**最后才是查证日期**——日期只回答"我什么时候看的",版本号才回答"我看的是什么",前者对读者几乎没有复核价值。
- **钉版本号要集中在一处**(比如文末「关于本文的准确性」里放一张"项目 → 核对基准版本"的小表,导读里指一句"版本基准见 §X"),正文只平铺陈述事实。"截至 vX.Y"是元信息,让它在正文里反复出现,读者每次都被打断一下,却得不到新东西。
- **别用以"写作这件事"为参照的时间词**:"本次核对时""近期版本加了 X""此前的一轮 review 发现""本文更早的版本写过 Y"——这些措辞的参照系是你的工作会话,而读者不在那个会话里,读到只会悬空。它们的来源通常是作者(AI 助手尤其容易犯)把干活时的时间感原样漏进了正文。改法:"近期版本加了 X"→平铺陈述"它有 X"(版本基准去集中声明处查);文章自己的修订史("更早的版本写过……后来改了")对读者是纯噪音,直接删——若那段历史恰好能当论据(比如证明"旁注确实会腐烂"),挪进集中声明那一节,别留在正文。
- **外部资源** → 优先给稳定入口(官方文档首页 + 章节名),而不是随时会改的深链。

自检一句:这份文档半年后被人翻出来,哪些句子会变成假话?能改成不会变的写法就改。

### 10. 操作类文档:每一步都要能真的走下去

只要文档里出现了"照这么做"的部分(装什么、跑什么、填什么),就多做一遍**可执行性自检**。这是作者盲区最集中的地方:你机器上早就装好的东西,在你眼里根本不算一步,于是那一步就从文档里消失了。

逐项过一遍:

- **每个让读者敲的命令,交代过它从哪来吗?** 一个凭空出现的 CLI 命令能把整篇文档卡死在第一步——文档把系统讲得再清楚也没用,因为读者压根跑不起来。
- **每个占位符,交代过去哪查它的值吗?**(`<资源名>`、`<deployment 名>`、连接串里的库名)只写"填你自己的 X"等于没写。
- **每个示例值,说清了是"照抄"还是"必须换"吗?** 版本号、区域、API 版本这类看起来像常量的东西,读者默认会照抄。
- **判断成败的依据给了吗?** 只说"跑一下看看"不算。要说清什么算成功(状态码、输出里的哪个字段、日志里的哪句),以及常见的失败长什么样。
- **给了判据,还要看它精确到能不能照着算。** 比"没给判据"更隐蔽的一种失败:你给了,但它在关键处留了二义。真实教训:一份文档教读者"看标注的那段有没有出现在返回的前 5 条里"来量检索效果,读着完全可操作;可"出现在里面"到底是**严格相等**还是**被包含**,文档一个字没说——而这两种读法在参数一变之后结果完全不同,照着做的人就卡在这儿。所以凡是"比较""匹配""命中""算作通过"这类判定,把**怎么算**写出来,别停在"看它在不在里面"。
- **凡是承诺"一次投入、以后能复用",写出它对什么变化免疫。** 上面那个例子还有第二层错:文档说"这一步只做一次,以后每次调参都能复用",可它同时又让读者去调那个**会让标注失效**的参数——于是这个承诺根本兑现不了。"可复用"从来不是无条件的。写这句话时先问自己:**读者接下来会改什么?我让他攒的这份成果扛不扛得住那个改动?** 然后把条件直接写进正文("要标在原文上、别记第几个块,因为块边界会变")。不写条件的复用承诺,等于给读者埋了个坑。
- **前置假设写出来了吗?**(已经装好 X、已经有 Y 账号、需要 Z 权限)写出来才好判断这篇是不是写给自己的。

超出范围的前置步骤不必都补全,但要**明说不管**("agent 本体怎么装不在本文范围内"),别让读者以为漏了。

### 11. 少造词,多借常识;借了就要对账

讲解一个复杂领域时,常常需要一套自己的框架(几条维度、几种范式、几个阶段)。这里有两个反复出现的坑。

**第一个坑叫「空编号命名」:用没有内容的编号来命名概念。** `轴 A / 轴 B / 轴 C`、`方案二`、`模式甲`、`Type 1/2/3` 这类标签本身不携带信息,读者必须在脑子里维护一张对照表。代价不是一次性的:标签会在正文、表头、结论里反复出现,每出现一次读者就要重新解析一次指针,甚至回翻。

**改法是让名字自带含义**:与其叫"轴 A/B/C",不如叫`表示轴`(用什么表示知识)、`时机轴`(什么时候把知识想清楚)、`引擎轴`(引擎能不能换)。这样"时机轴上那个选项"读者不用回翻,表格表头也不必再挂一个 `(轴B)` 的括号。自检很简单:**把这个标签单独拎出来放在第三页,读者还想得起它指什么吗?** 想不起来就该改名。编号只适合真正没有语义差别、纯粹用来点数的东西(步骤 1/2/3)。

改名时还要注意**结构平行**:同一套框架里的几个名字,词性和字数最好同构。`表示轴 / 时机轴 / 引擎轴` 三个都是三字同构,一眼看得出是一套;而 `表示方式 / 综合时机 / 引擎可换性` 虽然也自带含义,却一个是"某个属性"、一个是"属性的有无",长短也不齐,塞进表格表头就不像专有名词,容易和周围的普通词混成一片。**名字要能当术语用**,平行是它像术语的一半原因。

**第二个坑叫「类比欠账」:借了一个类比,却没检查它的推论。** 借现成的常识框架通常比自造一套好,读者的理解成本低得多——但借来的不只是形状,还有那个框架蕴含的全部性质,而读者会**自动**把这些性质套到你的主题上。

所以借之前先对账:这个类比默认了什么?我的主题是否都满足?举个真实的例子:用"三条轴"讲检索范式,如果进一步说成 X/Y/Z 三个坐标轴,读者会顺带导入"轴上是连续有序的数值""一个对象由三个坐标唯一定位"这些推论;可实际上那三个维度的取值是离散类别,而且一个方案完全可以同时落在多个取值上(混合、可插拔)。这时坐标系的类比会让读者更快地"觉得懂了",同时按错的结构往下推。

**熟悉但错的类比,比朴素命名更危险**,因为朴素命名只是让读者慢一点,错的类比会让读者自信地走错。这和原则 3 的歧义例子是同一种失败,只是发生在框架层面而非句子层面。处理办法二选一:**要么只借站得住的那部分并说清边界**("这里说'三条轴'只是指它们彼此独立,不像坐标轴那样有刻度,一个方案也可以同时落在两个取值上"),**要么放弃类比,老老实实按内容命名**。

**这两个坑常常撞在同一处,所以要一起处理。** 注意「空编号命名」的解法和「类比欠账」的风险不是两件独立的事:你为了让名字自带含义,最省力的办法往往就是借一个现成的词("轴""层""管道""流水线"),而这一借,「类比欠账」立刻跟着来。所以真实的选择不是"编号 vs 自带含义",而是这两条:

- **借 + 设栅栏**:用那个形象的词,紧跟着把它不成立的推论点掉。
- **不借 + 朴素命名**:按内容起名,不欠任何解释,但读者少了一个抓手。

实践下来**"借 + 设栅栏"通常更值**,前提是栅栏真写好了。一次读者测试里(测的正是"三条轴"这个例子),读者老实交代:读到"轴"时它脑子里第一时间浮现的就是三维直角坐标系、一个方案是空间里的一个点;是紧接着那段边界说明把它拦回来的,所以最后答对了"同一条轴上可以占多个取值"。这同时说明了两件事:错推论**真的会**在读者脑子里生成,「类比欠账」不是杞人忧天;但一道写清楚的栅栏**真的拦得住**。

**栅栏的位置是承重的,不能只放在概念讲完之后。** 同一次测试里,读者把这一处列为全文最大的卡点——栅栏那段离命名处隔了十几行,而且"又长又密","如果我漏读了那段,这道题我就会答反"。所以分两处写:

1. **命名的那句话后面,立刻跟一句即时提醒**:"(叫'轴'只取彼此独立这层意思,**不是**坐标系,每条轴上都可以多选,后面细说。)"
2. **概念讲完后,再给完整边界**:把不成立的推论**分点列出**,一条一句。读者会整段跳过密排散文,但很难跳过几个短要点。

自检照原则 13「就地」那一问来:**假设读者只看到命名那一句、完全没读到后面的边界说明,他会不会就此推错?** 会,就说明第 1 步那句即时提醒还没到位。

### 12. 长文的一致性:概括层要和细节层对账

别的原则大多管"单处写得好不好"。这一条管另一类错——**每一处单看都对,两处放在一起就矛盾**。它在长文里几乎必然发生,而且作者最查不出来:你只记得自己刚改过的那一处,记忆会自动把两处对齐。

**坑一:概括层会滞后于细节层。** 长文的事实分两层。细节层是某节正文里的具体描述;概括层是导读、横向对照表(**表里每一个格子都算一处**)、票数或计数、每节末的"一句话总结"、以及全文各处"见第 N 节"那类交叉引用。改了细节,概括不会自己跟上。真实教训:一次读者测试的五处发现里,**没有一处是"某个细节讲错了"**,全部是这类脱节——导读说"有两处相反答案的分歧",可那个分歧点早先已经被删掉、导读没跟着改;某节标题写"永不硬删",而它自己举的例子就是"14 天后硬删",标题被它自己的举证推翻;某处把两家不同的判定口径压平成一句话,恰好压掉了读者要照着实现时必须决定的那个差别;还有一处说"十三个文件",紧跟的枚举加起来是十二。

这类错对读者的伤害比"表述不清"大得多:两处都写得很确定,读者只能猜哪边是真的,而且**通常会信概括层**——它出现得更早、更像结论。

**删一个论点时最危险。** 删正文很容易,忘记回头改导读里对它的计数几乎是必然。

**坑二:票数断言是全文最容易错的句子。** "三家都这么做""四家一致""只有一家""别家普遍较弱""没有谁"——这类句子读起来最有权威感,而验证成本被作者默认为零。它们必须**逐条点名数一遍**,并确认正文里真的写出了那一家的证据。这里有两个反复出现的机制:

- **修一个过度断言,会造出新的过度断言。** 真实教训:改掉"某家是唯一用数据库的"之后,顺手写下的"某家没有失效机制"又是错的;再修一遍,又写出"只有它会问这条对不对"。同一个项目里连踩三次。所以**修完之后必须再扫一遍自己新写的句子**,这类修正天然会引入新断言。
- **待办清单会悄悄替换掉你的分母。** 第三次踩坑的原因很具体:我按待办清单只核了清单上那两家,漏掉了压根不在这轮清单上的第三家,而它恰恰也做了这件事。**分母是全集,不是你这轮打算碰的那几个。** 写"只有一家"之前,强制把全集逐个念一遍,包括你完全没打算碰的那几个。

**坑三:许下的贯穿承诺要逐节兑现。** 原则 5 让你立一个贯穿全文的例子,导读里往往还会跟一句"后面每讲一家都会回到这个例子"。这句话是**承诺**,漏掉一节读者就会在那一节一直等。真实教训:七节里有一节从头到尾没回到那个例子,读者读完才发现它不来了,只好自己推——而这一节恰好是他后面答不好的那一节。

**这一条的自检是机械的,所以真做得到:**

1. grep `三家|四家|五家|别家|大家都|唯一|只有一家|没有谁|都不`,对每一处点名列出成员、回正文查证。数不够就改成实际家数,或降级成"在本文对证过的范围内"。
2. 凡是"N 个文件""三条""四家"这类数字,把紧跟的枚举**真的加一遍**。
3. 改过或删过任何细节之后,回头查所有概括它的位置:导读、对照表、计数表、该节的"一句话总结"、以及别节里引用它的那句话。
4. 导读里许下的"每节都会 X",逐节确认真的做了 X。
5. **收尾前再跑一次穷尽式对账,把上面那几条从"改哪查哪"升级成"全部查一遍"。** 做法是先把概括位置**列全**成一张清单,再逐个回到它的来源核:导读的每一条承诺、横向对照表的**每一个格子**、每张票数或计数表的每一行、每节末的"一句话总结"、以及全文每一处"见第 N 节"是不是真指到那儿。第 3 条是"改了什么就查什么",这一条是"不管改没改都查一遍"——两者不能互相替代,因为漏掉的恰恰是你不记得自己动过的那些。

最后两句要紧的。**第一,"重读"查不出来,"枚举"查得出来,这是两件不同的事。** 重读时你的记忆会自动把两处对齐,所以读几遍都白读;可一旦把概括位置列成清单再逐个回源,它们就藏不住了——这就是上面第 5 条存在的理由。**第二,别指望读者替你把这类问题一次捞干净。** 读者确实最擅长抓它,但它是**线性读**的,一轮只捞出它路过的那一批。真实教训:一篇长文连跑三轮读者测试,每轮都捞出一批同类脱节、每轮都以为这次干净了,而真正一次排空的是自己跑的那遍枚举。所以两样都要:出题时专门留一道"文章里有没有哪两处互相对不上?",同时自己把第 5 条那张清单走完。

### 13. 「就地」:警示要贴着触发点,不能只放在远处

这一条是从前面两处独立长出来的同一个规律,值得单独命名,因为你以后遇到的每一个"该提醒读者小心"的地方都归它管:

- **原则 8 的实例**:某一段的内容没核实过,就在**那一段**点一句。只写在文末的可信度声明里,半路就去动手的读者永远看不到。
- **原则 11 的实例**:栅栏要**紧跟着命名那句话**。隔了十几行,读者漏读那段就会照着错推论一路走下去。

两处的实测证据指向同一件事:**读者会整段跳过密排散文,但很难跳过紧贴在正文里的一句话。** 所以远处那段完整说明仍然要写——它是给回头查的人看的——但它拦不住第一次读的人;真正拦住人的,是触发点旁边那一句。

**自检:假设读者只读到触发点那一句、完全没读到远处那段说明,他会不会就此走错?** 会,就说明"就地"那句还没到位。

这个词记住了会自动推广:以后你写完任何一处"这里有坑"的说明,先问一句它**离坑有多远**。

## 工作流:先校准,再全量

先**定读者**(见上一节)。然后按手上是什么料("改写旧稿"/"从零新写"/"对话内容落文档")走不同的**准备步**,最后都汇入同一条**主干**。核心节奏是**先拿一节校准基调,再铺开全篇**,省得方向错了返工——除非校准已经在别处做过了(见第三种情况)。

**准备(按情况三选一):**

- **改写 / 重构已有文稿** → 先**诊断体裁**:现状是什么体裁、问题在哪(例:"电报体——术语不解释、`→` 连环、详略一刀切")。这种病常是作者和某人一路讨论的产物,默认了共享上下文,所以作者看得懂、新读者看不懂。再**提处理原则**(打算怎么改语气/术语/详略),并**给逐节详略表**(表格列出每节"现状 → 扩/缩/保持",让用户一眼看清计划;用户偏好决策表:节 | 现状 | 处理)。
- **从零新写** → 先**列大纲,按"信息 DAG"排序**(见原则 6):定好章节和顺序,保证前置概念排在依赖它的内容之前。和用户确认大纲。
- **把刚才对话里的内容落成文档**(用户说"帮我写成文档""总结到某个目录下") → **不要再列大纲问一遍**,跳过主干第 1 步(校准样例),直接从第 2 步开始铺开。理由:对话本身已经是校准过程,用户刚看完你的分析、认可了它的内容和结构,再问一次"大纲这样行吗"是把同一个确认做两遍。判据是**你能指出对话里哪一段就是这篇的骨架,且用户对它表示过认可**(比如紧接着说"写成文档");如果对话只是零散讨论、还没有成形结论,那不算,回到"从零新写"。

  这个分支省掉的是**校准**,不是**改写**,也不是**分批产出**(长文照样要骨架先行,见下面「长文档:骨架先行,逐节充实」)。对话里的形态几乎一定是电报体:箭头串句、分号碎片、给了代码行号、术语没解释、详略一刀切,因为那是即时问答本该有的样子。直接粘过去,等于把一份聊天记录存成 `.md`。所以落文档时全套照做:重排成信息 DAG、补术语解释、行号换成符号名(原则 9)、立一个贯穿全文的例子、把细节择成旁注。**做完后主动说明你改了什么、为什么改**(列一张"相比对话里的版本做了这些调整"的小表就够),否则用户会以为你只是复制粘贴,不知道内容已经被重写过一轮。

**主干(三种情况共用):**

1. **先写 / 改一节做样例**:挑最抽象、最难的一节,按目标基调写好,让用户校准语气和深度是否到位。(第三种情况跳过这步,校准已经在对话里做完了。)
2. **确认基调后再铺开全篇**——用户认可基调了,才动整篇。但"铺开"不等于一次性写完:长文要**骨架先行、逐节充实**(见本节末的同名小节),这跟基调校准是两件独立的事。
3. **逐条过文末的反面清单**——它是一个**步骤**,不是一份"有空看看"的附录。**完成判据是穷尽式的:那一节的每一条你都要能说出"这篇为什么不犯"**。(这里刻意不写条数——条数会随清单增删而腐烂,而一个过期的条数会让你以为自己走完了。数一遍那节的条目,以你看到的为准。)

   为什么要把它抬成一步:清单写得再好,只要不在步骤链上,注意力就会在"我已经交稿了"那一刻滑过去。真实教训:一次收尾"做了自检",实际只跑了六条(行号、单破折号、箭头串句、票数断言、以写作事件为参照的措辞、命名约定),而且挑的全是作者自己被烧过的那几条,清单排在前面的反而没走。**"我做了自检"和"我走完了清单"是两件不同的事**,前者靠印象,后者靠清单。

   自己走的顺序:先把能机械跑的跑完(行号、箭头串句、票数断言、计数与枚举对不对、"截至 vX / 本次核对"这类措辞,都能直接 grep),剩下那些要靠读的再逐条读。机械的那批先跑,是因为它们不占脑力却最容易漏。

   **它为什么排在读者测试之前:** grep 和读者抓的是**不重叠的两类**。行号、箭头、会腐烂的断言、算错的计数,grep 免费就抓得到,而读者反倒抓不准——那些不是理解问题。反过来,理解缺口和跨节矛盾只有读者抓得到。先跑免费的那一遍,**等于不让昂贵的读者去干 grep 的活**,而且让读者看到的是一份已经清过一遍的稿子。

   **它同时是一道会回流的闸,不只是一个一次性的阶段。** 只要你又写了一批东西——**包括第 4 步之后为了修读者发现而写的那批**——就回来把机械那几项再跑一遍。理由很直接:修读者发现的时候,你照样会夹进一个行号、一句没核实的断言。所以它既需要一个编号位置来保证被想起,也需要这条回流条款来保证覆盖到最后一批修改。

4. **读者测试,这是最后一道门**——把"读者读得懂吗"从主观愿望变成可检验的一步,是整个流程的完成判据。关键不在"用什么工具",而在**换一双不带作者背景的眼睛**:找一个没有本次写作上下文的"读者",让它回答 3~5 个真实读者会问的问题;它**读错、答偏、或主动说"这里有歧义""这里默认我已经懂 X"的地方,就是要修的地方**。谁来当这个读者,看情况:
   - **有人在逐轮审阅**(用户就在 loop 里改你的稿):用户本身就是那双无背景的眼睛,人工 review 其实已经在做读者测试,正式的 subagent 测试是**可选**的加保险。
   - **无人在 loop**(自主写作,或交付 / handoff 前的最后一道关):这时**必须真的**派一个 fresh subagent(只喂它这篇文档、不带对话上下文)或开一个全新对话来测,别跳过——否则完成判据就落空了。
   - 两者都没有:退而求其次,自己**假装第一次读**,逐段问"这句我看得懂吗、会不会有第二种理解"。

   **文章接近完成时,主动问用户一句**:"要不要我起一个无上下文的 subagent 跑一遍读者测试?" 把这道正式验证的选择权交给用户——它有额外的时间和 token 开销,值不值得由用户定,别默默跳过、也别默默硬跑。

   派 subagent 时,把隔离条件写死:**只准读这一个文件**,不许翻代码库、不许 grep、不许搜网、不许沿用对话上下文。少了这层隔离,它会自己去把你没写清的地方补上,测试就白做了。同时要求它:凡是靠推测回答的,必须明说"这里我在猜,是因为文档没写"。

   **它为什么必须排最后:整个流程里只有它以成品为对象。** 排在它后面的任何一步都会产出修改,而那些修改就成了**没有任何读者看过**的内容——这正是收手判据第 3 条禁止的事。所以过了这道门之后,只允许两种动作:修完读者指出的问题、然后回第 3 步把机械那几项再跑一遍;如果修出来的是大段新内容,按收手判据第 3 条再测一轮,别就此收尾。**别在这道门之后开新战场。**

### 长文档:骨架先行,逐节充实

一篇几百行的文档,别试图一次写完。先把**骨架写进目标文件**:所有章节标题按信息 DAG 排好,每节底下留一句"这节讲什么";再把导读和最难的那一节写满,其余留占位。然后逐节把占位换成正文。

三个理由,前两个是写作上的:

1. **骨架就是信息 DAG 的实体化。** 原则 6 要求前置概念排在依赖它的内容之前,可这个顺序只存在你脑子里或对话里时是**没法检查**的;写进文件才能一眼看出"第 5 节用到的概念要到第 7 节才讲"。更要紧的是:**在骨架里挪一节几乎不花钱,在三千字正文里挪一节你就不会挪了**——你会将就着不动,于是 DAG 就烂在那儿。
2. **占位那句"这节讲什么"不是脚手架,是正文。** 原则 6 本来就要求长文每节给一句"这节讲什么"。先写这句,等于逼自己在动笔前说清这一节的职责,而这正是防止一节写散、防止详略一刀切(原则 4)的手段。所以它大部分会原样留在成品里,不是写完要删的临时物。
3. **进度落在磁盘上,失败粒度小。** 一次产出整篇是一次很长、不可分割的输出:中途失败,你已经想好的内容会全部一起丢,而重试同一个巨大的写入往往以同样的方式再失败一次。骨架加逐节编辑,每次写入都小,写完的部分留在文件里,失败最多影响当前这一节。

**判据**:目标篇幅到几百行、或章节数超过五六个,就走骨架先行;短文直接写完更省事,不必绕这一圈。

**它和"先写一节做样例"是两件事,别混。** 样例是为了**和用户校准基调**,基调已经对齐时可以跳过(比如第三种准备情况)。骨架先行是为了**可靠产出**,和校准无关,所以**三种准备情况都要做**,包括那个跳过校准的分支。踩过的坑正是把这两件事当成了一件:因为"校准已经做完了",就直接上手写整篇。

**别绕临时文件那个弯。** 有个看着合理却不解决问题的做法:先把手上的材料摊进一堆临时文件,再从临时文件汇总成文。它治不了上面第 3 条,因为瓶颈不在"材料放在哪",而在"你一次要产出多大一块";材料放哪都行,一次写整篇照样失败。(材料该不该落盘是另一个问题,见下。)

### 材料随手落盘

长文常常建立在前面做过的调研上(读了六个仓库、翻了一批资料、跑了一串命令)。这些发现此刻只活在对话上下文里,而上下文会满、会被压缩。

**这不只是"怕丢东西"的效率问题,它直接决定你还能不能守住原则 8。** 材料一丢,你就开始凭记忆写;凭记忆写出来的句子,读着和核实过的一模一样自信,可你自己已经分不清哪句有出处、哪句是脑补——于是文末那张"核实过 / 实际跑过 / 没核对"的三桶表就填不出真话了。

- **材料一旦成形就落盘。** 优先直接落进正文该待的位置;正文还没到能接收它的阶段,就写进一个命名清楚的笔记文件,并在文件里注明它是中间产物。
- **交接时要给出材料的路径。** handoff 文档里"结论是什么"和"结论存在哪"是两件事:只写结论,接手的人会以为得重新调研一遍;给了路径,他才能接着往下核对。

### 读者测试的四条使用要诀

**一、读者的问题是金子,读者的答案不是证据。** 它答不上来、或者只能靠猜的地方,准确指出了文档的缺口——这部分照单全收。但它猜出来的**内容**不能直接写进文档。真实教训:一次测试里它猜"配置引用了没设的环境变量会让服务起不来",听起来很合理,去查代码并实际跑了一遍才发现是静默解析成空值、服务照常启动。**如果它问的问题你自己也答不上来,那是你要去查源码、去实测的信号,不是抄它答案的时机。**

这一条还有一个更隐蔽的变体,值得单独记:**读者说"这两处对不上"时,它给的是一个诊断,而诊断也是答案,同样不算证据。** 你很容易顺着它的诊断去修,却修错方向。真实教训:读者指出某处把一个"14 天"规则挂在状态 A 上、另一处挂在状态 B 上,判定其中一处有误;我据此把 A 那边删掉了——**结果配置文件里两个状态各自都有一条 14 天规则,两处原本都对**,只是文章从没告诉读者这是两条独立的规则,读者只能当成矛盾。**看到"表面矛盾"时先假设两边都对,去核第三方**(源码、配置、原始文档)**,再决定是删一边还是加一句消歧。** 否则你会为了消掉一处"看起来的错"而制造一处真的错——这比原来那个含糊更糟,因为它连痕迹都不留了。

**还有一个对称的坑:被读者误导过一次之后,你会开始按自己的怀疑改稿,而你自己的怀疑同样不算证据。** 真实教训:核完读者一处误判之后,我自己盯上另一处"只有一家"的断言,越看越觉得它也过度了;去源码查完,**原文是对的**。所以这条规矩的准确形式不是"别信读者",而是**任何没经第三方核实的判断都不能拿来改正文,不管它来自读者还是来自你自己**。

**二、它不只抓"讲不清",也抓"讲错了"。** 别把读者测试当润色工具。一次测试里它只是追问"那个响应头返回什么值才算对",顺着这个问题查下去,才发现文档让读者去看的那个字段其实是一串哈希、人根本读不出信息——是条错建议,不是表述不清。所以它每一个"这里我看不出来"都值得当成潜在的事实错误查一遍。

**三、多轮要换问题,并且知道什么时候收手。** 同一批问题只会反复检验同几条路径,第二轮基本是在确认第一轮的修补。要真找到新东西,下一轮就问**没被问过的角落**:边缘场景、文档没直接举例的组合、"我要扩展到文档没提的情形怎么办"、"我领导问我 X,这篇能回答吗"、"照这篇选型半年后这套东西会怎么烂掉"、"我把这篇给一个只会照抄的同事,他最可能抄错哪一处"。实践中最大的缺陷往往是第三、四轮这样问出来的,不要因为前两轮平淡就提前收手。**另外每轮固定留一道内部一致性的题**:"文章里有没有哪两处互相对不上?"(理由见原则 12)。

**最有杀伤力的一种出题法:不换任务,换读者能看到多少。** 上面那些角度都是换任务,这一种是**限制阅读窗口**——给读者一个角色加一条硬约束:"我只有五分钟,**只读那张横向对照表**就要筛出满足某条硬需求的方案","我只会看导读和各节标题,我会得出什么结论"。让它先在这个窗口里作答,**再让它翻回正文核一遍自己刚才答得对不对**。

它为什么特别准:原则 12 说读者**通常会信概括层**,因为概括出现得更早、更像结论——而受限窗口正好把这种读者造出来,于是概括层任何一处丢了限定词都会立刻现形。真实教训:一次这样出题,读者只扫一张表就得出两个**反向**结论:一家因为那格漏了"手动可删"这个限定而被判为不合格,另一家因为那格写着"30/90 天冷落归档"而被判为合格,可正文恰恰拿这家当"冷落治不了错误"的反面例子。这两处前面六轮全文重测都没碰到,原因很朴素:那六轮的读者都读了全文,**自动用正文补上了表格缺的限定词**,于是缺陷被他们自己的理解力掩盖了。说到底这一招就是**把原则 13 那个自检交给真读者去做**——那条自检问"假设读者只读到触发点那一句、没读到远处的说明,他会不会走错",你自己问,答案总是偏乐观;交给一个真的只读到那一句的读者,答案才可信。

**收手判据集中在这里,三条要同时成立才算可以收**(别处不再重复,遇到相关的话题一律回来看这三条):

1. **看发现的性质,不看轮数。** 当反馈从"缺信息 / 讲错了 / 两处对不上"降级为"这段太密了 / 这里重复了"这类风格问题时,边际收益才算掉下来。
2. **"两处对不上"属于要修的一类,不是收手信号。** 它往往正是后几轮才浮出来的东西,一次读者测试的五处发现可以全部是这一类。
3. **这一轮又新写了大段内容的话,不能收。** 那些风格反馈针对的是老内容,你新写的部分还一次都没被人看过——为什么这一条不能省,见要诀四。

   **这一条还顺便告诉你循环什么时候会结束,所以别只把它当闸门看。** 判据 1 说"看性质不看轮数",可它没回答"那还剩几轮"。答案在你自己的改动上:**只要这一批还在整段整节地写,就还有下一轮;等改动缩到从句、表格里的一个格子、一句限定语,循环才真的收口。** 真实教训:一篇长文收尾连跑三轮都收不了,存量缺陷从 13 一路降到 8、7、3、1,而每轮停不下来的原因始终是同一个——修完一看,自己又新写了整段。所以进度感要这么读:**看修改粒度,不看剩余问题数。** 粒度不降,问题数降下去也会被你新写的内容补回来。

**四、上一轮为了补缺口新写的段落,是下一轮最该测的地方。** 每测一轮你都会新写一些内容去填缺口——而这些新段落**还没有被任何读者看过**。旧内容至少已经过了一轮筛,新内容是零筛;更麻烦的是你刚写完它,脑子里全是上下文,正处在盲区最深的时候。真实教训:一次两轮测试里,第二轮唯一那个逻辑错误,恰好就在第一轮新加的那节里,而被测过一轮的老内容一处都没中。

所以下一轮出题时,除了问没被问过的角落(要诀三),还要**专门挑一两道题去踩你刚写的那几段**。出题方式很关键:别泛泛地问"这节讲清楚了吗"(它会回答"清楚"),要让读者**当成要照着做**来检查——"我要照着这段做,每一步我都知道怎么操作吗?哪一步含糊到我做不下去?" 新写的操作步骤尤其容易在这种问法下露馅。

**这个"照着做"的问法不止用于新段落,整轮题都可以这么出**,而且往往挖得更深。把每道题写成一个带具体参数的任务("我要让 agent 在 `/srv/api-server` 这个目录下遵守某条规范,给出你的操作步骤""线上出了这个症状,你去哪里、看什么才能确认或排除"),比问"你理解了吗"强得多。原因在于它换掉了读者的角色:**评价者会给你礼貌的肯定,执行者会在某一步真的卡住,并且能说出卡在哪。** 而且卡住的位置常常暴露的是整篇的系统性缺口,不是单段的表达问题。真实教训:一次这样出题,读者两道题都卡在最后一公里(该改哪个文件它答得很好,但"怎么让程序认到这个目录""日志里搜哪个关键词"全断在门口),这才看清整篇一直在讲原理、几乎没给过一个可执行的锚点——这种缺口用"这节清楚吗"永远问不出来。

这就是收手判据第 3 条的来历(见要诀三):**只要这一轮又新写了大段内容,判据就不成立**,哪怕这轮反馈全是风格问题。

反过来也要有主见:读者测试提的意见**不都要采纳**。典型的该驳回的一类是它嫌某些内容"对我是噪音"——如果那部分本来就是写给另一类读者的(见下节),那是定位的固有代价,不是缺陷。驳回时说清理由就行。

## 当读者同时包括 human 和 AI agent

越来越多的技术文档有两类读者:人要读懂,agent 要照着执行。两者的需求不一样,硬揉成一篇会两头不讨好,所以要显式分层:

- **顶部单开一节「给 AI agent 的执行摘要」**,把硬约束前置成几条断言式的短句(必须怎么做、**尤其是不要怎么做**)。agent 常常不会读完全篇,把它最容易做错的方向堵在开头,比埋在正文第五节有用。
- **正文照常写给人**:直觉、类比、为什么。agent 也能从中受益,但节奏按人的理解成本排。
- **给 agent 留可核对的锚点**——但按原则 9,锚点要用文件路径 + 符号名,不要行号。agent 拿着符号名能自己搜到并核对逻辑,拿着过期行号只会被带偏。
- **明确 scope 边界**,让 agent 知道哪些事这篇不管、别自己发挥。

人类读者可能会说前置摘要和那些代码引用"我跳过了"——这没问题,它们不是写给人看的那部分。别为了让单一读者满意而砍掉另一类读者赖以执行的内容。

## 反面清单(出现即停,回炉)

写完**逐条过**,每条都要能说出"这篇为什么不犯";命中任意一条就说明还没到位:

- 满屏 `→`、分号碎句,句子不成句 → **电报体,回炉讲解体**。
- 出现读者可能不认识、却没解释的术语 → **补一句白话**。
- 例子有第二种理解 / 符号会误读 → **改到无歧义**。
- 每段都一样详细,或核心机制一笔带过而边角料铺一堆 → **重新分配详略**。
- 通篇没有一个具体例子,全是抽象定义 → **加贯穿全文的例子**。
- 开头直接进正文,读者不知道"这写给谁、该怎么读" → **补导读**。
- 实现细节/进阶内容塞在主线里打断阅读 → **择成可跳过的旁注**。
- 把没核实的数字写成确定事实 → **标来源**。
- 引用了代码行号,或写了"目前最新是 X"这类会腐烂的断言 → **换成文件+符号名,或换成一条查法**(原则 9)。
- 正文出现"本次核对 / 近期版本 / 本文更早的版本"这类以写作事件为参照的措辞,或"截至 vX"散落在多处 → **平铺陈述事实,版本基准集中钉在一处**(原则 9)。
- 让读者敲的命令没交代怎么装,占位符没交代去哪查,示例值没说清能不能照抄 → **补可执行性**(原则 10)。
- 只说"跑一下试试",没说什么算成功、失败长什么样 → **补判断依据**。
- 给了判据,但"怎么算命中 / 算通过"能有两种读法 → **把判定规则写到能照着算**(原则 10)。
- 承诺"做一次以后都能复用",却没写它在什么条件下才复用得了 → **补上复用条件,或别许这个诺**(原则 10)。
- 未核实的内容只在文末声明,正文里读得像已核实 → **就地也标一句**(原则 13)。
- 正文里有你此刻已经指不出出处的事实断言 → **回去核实,或把材料落盘再写**(见「材料随手落盘」)。
- 一串必须逐项照做的东西被塞成一段 prose(要改的五个位置、要装的三个依赖) → **改成表格或清单**,让它能被当检查表用。
- 自造的概念用编号命名(轴 A / 方案二 / Type 1),读者得维护对照表 → **改成自带含义的名字**(原则 11)。
- 借了一个类比,但它的某些推论在本主题上不成立 → **说清边界,或换成朴素命名**(原则 11)。
- 借了类比也设了栅栏,但栅栏只在概念讲完之后、离命名处隔了十几行 → **命名那句后面补一句即时提醒**(原则 11、13)。
- 写完一处"这里有坑"的说明,却没检查它离坑有多远 → **问一句"读者只读到触发点那句会不会走错"**(原则 13)。
- 同一套框架里几个名字词性/字数不平行,放进表头不像术语 → **改成同构的短名**(原则 11)。
- 出现"三家都这么做 / 只有一家 / 别家普遍较弱"这类票数断言,却没逐条点名核过 → **点名数一遍,数不够就改实际家数或降级说法**(原则 12)。
- 刚修完一处过度断言 → **回头再扫一遍自己新写的句子**,这类修正天然会造出新断言(原则 12)。
- 写"只有一家"时只核了这轮待办清单上的那几个 → **把全集逐个念一遍**,分母不是清单(原则 12)。
- 改过或删过某处细节,但导读、对照表、计数、小节标题、"一句话总结"没跟着改 → **回头逐处对账**(原则 12)。
- 出现"N 个文件""三条"这类计数,紧跟的枚举没真的加过 → **加一遍**(原则 12)。
- 导读许诺"每节都会回到这个例子",却有某节没回到 → **补上,或改掉那句承诺**(原则 12)。
- 引用的材料自己又引了论文/benchmark 当依据,而你只核到"它确实这么说" → **顺着再核一层,或明确归属为"这是某某自己的判断"**(原则 8)。
- 文末的可信度分桶里,空的那一桶被省略了(比如从没跑过任何系统,却没写"实际跑过的:无") → **把空也写出来**,否则下游会当你跑过(原则 8)。
- 同一份材料里两处说法相反(注释 vs 代码、文档 vs 实现),你只写了自己采信的那一个 → **就地交代另一处说了什么、你为什么不采信**(原则 8)。
- 写下了"它没有 X""没找到任何机制",却没交代自己搜了多大范围 → **写明范围并承认没穷尽,顺便挂上版本基准**(原则 8、9)。

## 一个"电报体 → 讲解体"的对照示例

**改前(电报体,读者看不懂):**

> **向量(embedding)**:文本→向量,语义近则距离近,靠 top-k 召回。最主流。

**改后(讲解体,先直觉后术语、术语有解释):**

> **向量(embedding)**:把每段文字压成一串数字(叫"向量"),让语义相近的文字对应的数字也相近。于是"找相关内容"就变成一道几何题——把问题也转成向量,去库里找**距离最近的那几段**。这是目前最主流的做法。

差别不在信息量,而在**读者能不能一次读懂**:改后先给了"压成数字""几何题"这样的直觉,再落到术语,新读者才接得住。
