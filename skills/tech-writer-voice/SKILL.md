# tech-writer-voice：把稿子改成人说话的口气

## 这个 skill 做什么

接一篇已经写清楚、也不油腻的中文技术稿，只调**语体**：让它读起来像一个懂行的人在跟你讲，而不是像一份交上去的文档。不动结构、不动技术事实、不做删减。

## 唯一的判据

每一句只问一个问题：**把它念出来，你会这么跟同事说吗？**

不会，就是这一步要处理的。会，哪怕它命中了下面任何一条规则，也留着。

这条判据能覆盖规则表没收录的句式，所以先记住它，再看规则。

## 和 deslop 的关系：两把尺子，互相咬合

`tech-writer-deslop` 问的是「这句话有没有携带只有作者知道的信息」——抓**空转**。本 skill 问的是「这句话你会这么说吗」——抓**语体**。

两者正交，有实测支撑：

- 一篇作者判定「用词生硬、看不下去」的稿子，deslop 扫描器七项密度全 ok，逐条命中只有 7 处、还都是它自己标注的高假阳性。**它看不见生硬。**
- 反过来，生硬的句子往往信息很实。「走哪条取决于 LiteLLM 给这个 provider 实现了什么」按 deslop 的判据完全无罪，但它是文档腔。

更要紧的是第三条：**口语化会系统性地制造 deslop 要抓的病**。实测过一次——把长句改写成「主句——补充说明」之后读着确实像说话了，但破折号从 1.1/千字冲到 3.3，越过 deslop 的 2.5 线。所以第 4 步的复扫不是走过场，是这两个 skill 必须咬合的地方。

## 三条判据

这三条是从真实作者反馈里长出来的，覆盖了绝大多数「生硬」。

### 一、句子要有起点

中文口语先落地再展开。裸的存在句、无主语判断句、书面连接词起头，读者找不到「谁在说、在说什么」。

- 「有两个维度容易被混为一谈」→「这里有两个维度，特别容易混在一起」
- 「几个字段值得解释」→「有几个字段我多说两句」
- 「基于上面的分层，落到实处就是」→「照上面那个分层，落到实处就是」

起点可以是主语（我／你／我们）、话题词（这里／这套／这一节）或指示代词。**「我们」可以用**——它是拉着读者一起走；要防的是「大家」。

注意边界：**裸存在句本身不是病**。「有两个坑容易踩」在口语里完全成立。上面第一例难受在「混为一谈」这个成语和「被」字，不在「有」。正则分不出这个差别，所以脚本里 `reg-topicless` 只收书面连接词，存在句交给「无人称段落」那项指标兜。

### 二、别把「侧」「方面」「层面」当名词用

「网关侧」「客户端侧」是画架构图时的切分词，不是开口说话的词。

- 「网关侧是我自己在用的」→「网关这部分我自己一直在用」
- 「在性能方面」→「说性能的话」，或者直接删

### 三、成语和书面动词换大白话

成语是压缩过的书面表达，念出来有背诵感；书面虚词成批出现会把口型从「跟你说」变成「兹通知」。

- 「混为一谈」→「混在一起」
- 「取决于 X」→「看 X」「要看 X」
- 「即可」→「就行」；「无需」→「不用」；「较为」→「比较」
- 「以厂商文档为准」→「你看厂商自己的文档」
- 「业界目前有三种主流形状」→「眼下主流的形状就三种」（「业界」通常可以直接删掉而不损失信息）
- 「本文」→「这篇」；「笔者」→「我」；「上述」→「上面那个」

完整词表和判例在 [references/zh-register.md](references/zh-register.md)，拿不准就查，别凭印象。

## 三条红线

这些不是风格建议，是踩过的坑。

**技术事实只能保留，不能改。** 代码块、命令、参数名、配置项、版本号、数字、报错原文——原样搬运。语体改写只发生在叙述性文字上。改完用脚本把代码块拿回改前版本逐字节比对，别靠眼睛。

```bash
python3 {baseDir}/scripts/fidelity.py <改前.md> <改后.md>
```

**不加新事实，尤其不替作者编他自己的经历。** 口语化最自然的手法是把陈述改成自述——「给每个 agent 单独配一套？」改成「我一开始就是这么配的」，一下子亲切了。但那是一句关于作者本人的断言，你不知道真假。实测里撞见过一次：保留了原来的反问句、只给它加主语（「那给每个 agent 各配一套？可以，但……」），然后把「要不要改成自述」单独列出来问作者。**这类改动全部单独列出来问，不要混在批量改写里交付。**

**指定了范围就只改那个范围。** 作者说「看看第 3 节」就只动第 3 节。文稿改动散在全篇，作者不容易发现你越界。

## 执行流程

### 第 0 步：跑脚本

```bash
python3 {baseDir}/scripts/voice.py 文件.md
```

`{baseDir}` 是本 SKILL.md 所在目录。常用参数：`--json` 给程序用，`--max-per-rule 5` 控制每条规则列几处，`--deslop` 顺带跑一次 deslop 密度回归。

脚本自动排除代码块、行内代码、URL、frontmatter，行号可以直接跳过去。

四项指标里 **「无人称段落」最灵**：同一篇稿子，作者判定「看不下去」的版本是 76.5% 和 59.5%，改到作者认可是 48.6% 和 40.0%。整段不出现「你／我／我们」，读起来就是说明书。别的指标动静都没这么大——「长句率」改前改后只差 4 个百分点，是弱信号；「书面腔命中」分得开但要看具体命中了什么。

脚本只找嫌疑，不定罪。正则分不清「以你自己跑出来的结果为准」（读着顺，该留）和「以厂商文档为准」（该改成「你看厂商自己的文档」）。**定罪是你的活。**

### 第 1 步：先出校准样例，别直接刷全篇

**这是整个流程最重要的一步。** 挑 5–8 处最典型的，给「原句 → 改句」对照，问作者调子对不对。认可了再过全篇。

为什么不能跳：语体是主观的，作者对「亲切」的容忍度、能接受多少第一人称、愿不愿意用「我们」，你猜不到。实测过一轮——作者点了四处不满意的地方，从这四处读出三条判据，出了一批样例，作者回「认可，感觉好多了」，然后全篇一次过，没有返工。反过来先刷全篇再等作者挑刺，作者要么全盘推翻，要么在一百处改动里挑不出话说。

样例里要包含**一处你拿不准的**，让作者顺手把边界划了。

### 第 2 步：过全篇

按三条判据逐段处理。同时注意：

- **原文和派生版一起改。** 稿子如果已经有公众号版／简版之类的派生物，叙述句是同一批，只改一边下次重生成就退回去了。
- **该留的留住。** 面向 agent 的执行摘要、API 参数说明、报错清单这类地方，断言式短句是刻意的，口语化会削弱它们。判据还是那一条：这段是写给人读的吗？
- **别为了口语而口语。** 加「其实呢」「怎么说呢」「说白了」这类填充词不是口语化，是另一种腔。口语的力气在句子的骨架上——有主语、动词直接、一句话说一件事。

### 第 3 步：验技术保真

```bash
python3 {baseDir}/scripts/fidelity.py <改前.md> <改后.md>
```

比对代码块、行内 code、数字、版本号、URL。任何一项报 FAIL 就是改坏了技术内容，修完重跑。

有下游自检脚本的（比如 `wechat-finetune/scripts/verify.py`）也一并跑。

### 第 4 步：复扫 + 对账

```bash
python3 {baseDir}/scripts/voice.py <改前.md> <改后.md> --diff --deslop
```

两件事一起看：

1. **语体指标真的降下来了吗。**「我改过了」和「指标降下来了」是两回事。没降说明改的地方不是问题所在。
2. **deslop 的密度项有没有被自己顶上去。** 这是本 skill 最容易犯的错，见上面「和 deslop 的关系」。破折号超标就把单个破折号顶替逗号句号的那些改回标点——成对插入语和「术语——定义」两种正当用法留着。

**过线即停。** 阈值是线不是方向：只动超标项，达标项保持原样，超标项一跨回线内就收手。继续压下去，砍的不再是生硬，是作者的正常表达。

### 第 5 步：通读一遍

**判据只有一条：读起来比原文更做作吗？** 是就是改坏了，回退。

这个 skill 最典型的失败不是漏改，是用力过猛——把一篇稳重的技术文改成朋友圈口气。目标是让文字像一个懂行的人自然说出来的，不是让它显得热情。

## 交付格式

```markdown
## 我读出来的判据
[从作者的反馈或原文里归纳的 2–4 条，说清每条针对什么]

## 原句 → 改句
[逐处对照。数量多的时候按小节归组，别列成两百行清单]

## 需要你拍板的
[涉及作者本人经历、语气分寸、要不要用第一人称的地方，单独列]

## 指标对账
[voice.py --diff 的输出 + deslop 密度回归结果]

## 我没动的
[命中了但判断该留的，逐条说理由；理由要指向这篇稿子的具体内容，不是复述通则]
```

## 什么时候别用这个 skill

- **结构乱、读者看不懂**：那是 `tech-writer` 的活。语体调得再好，读者接不住信息还是白搭。
- **满屏加粗、套路句式、空转**：那是 `tech-writer-deslop`。
- **太长了发不出去、要重拟标题**：那是 `wechat-finetune`。
- **英文稿**：规则表是按中文语法校准的，「无人称段落」这类指标套到英文上没有意义。
- **代码注释、提交信息、API 文档的参数说明**：这些地方的简省是功能性的，不是生硬。
